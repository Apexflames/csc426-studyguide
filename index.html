Topic 1

Introduction to Software Engineering

What is Software Engineering?

Source Material — Unified Definition Software Engineering is a field that deals with analysing, developing, testing, deploying, maintaining and management of high quality software.
Plain English It's the discipline of building software properly — not just writing code, but planning it, testing it, shipping it, and keeping it working, the way a civil engineer plans a bridge rather than just stacking bricks.

Pfleeger's Definition (1987) — the S.O.F.T.W.A.R.E. qualities

Source Material Software engineering is the strategy for producing quality software:
  • Scalability
  • Operability
  • Flexibility
  • Testability
  • Warranty
  • Availability (up-time high, drop-time low)
  • Reuseability
  • Extensibility

Philips (2007) and the IEEE definition

Source Material Philips defined SE as a method of producing good and large software, complimenting Pfleeger by stressing quality software. IEEE (an extension of Pfleeger) defines it as a field of engineering that deals with a systematic, disciplined and technical approach to developing and deploying quality software.

Why Software Engineering?

  • Teaches the "engineering of clean code" — a coding methodology
  • Teaches software architecture principles
  • Teaches how to measure software quality
  • Covers software security
  • Gives knowledge of version control

Areas of Software Engineering: Programming Engineering, Mobile Engineering, Cybersecurity Engineering, Machine Engineering, Quality Assurance Engineering. (Programming is individual coding; software engineering is the architecture around it.)

Birth of Software Engineering — the Software Crisis (1968)

Source Material Software Engineering was born in 1968 after a NATO meeting in Germany, called because of concerned issues in the software industry in the late 1950s–early 1960s. The problems identified were called the Software Crisis:
  • Software Cost — no uniformity, no organisation controlling cost
  • Software Delivery Time — market deadlines were missed
  • Software Failure
  • Software Development Model — only Waterfall existed, causing delay/failure
  • Software Deployment Platform — limited to one platform
  • Software Maintenance — no principled agreement backing it
The meeting concluded that Software Engineering should be established as a field/domain under which all practitioners should sit.
Plain English Think of it like early Nigerian road construction before any building code existed — everyone built differently, some roads collapsed, nobody agreed on standards. NATO's 1968 meeting was the moment the industry said "we need standards," the same way a professional body sets construction codes.

What Has Changed Since Software Engineering Began

  • Late delivery → time-to-market delivery
  • Slow, rigid models → young, smart, Agile models
  • Sole-proprietary software → open-source software
  • In-house development → out-sourced development
  • Crowded junk servers → Cloud Computing

Software vs Software Product

Source Material Software = a program that dictates/directs how a computer works — it does not need support and documentation. A Software Product is a package with marketable artefacts: it needs licensing, documentation, pricing, delivery, maintenance and versioning. A software product is a software system developed, debugged and delivered to clients with adequate documentation guiding installation and usage.

The Software Development Flow (SDF) and its Actors

Flow: Requirement Definition & Analysis → Software & System Design → Program Design → Program Implementation → Unit Testing → Integration Testing → System Testing → System Delivery → System Maintenance (each stage feeds back to the one before it for problem-testing/documentation/delivery).

ActorResponsibility
System AnalystAnalysis; specifies the nature of the required software, with input/support recommendations
System DesignerGraphics/logo, suitable hardware configuration, recommends programming language
System ProgrammerProgram design and coding; has a part in unit testing
System TesterUnit, integration and system testing
System TrainerSystem delivery and maintenance

Note from the notebook: when there's a code problem, trace from the last stage back to the beginning.

Quick Revision SE = analysing + developing + testing + deploying + maintaining quality software. Born 1968 after NATO's software-crisis meeting. Software ≠ Software Product (documentation/licensing is the difference). Six actors run the SDF: Analyst, Designer, Programmer, Tester, Trainer (+ SDF stages themselves).

Topic 2

Requirement Elicitation

Definition

Source Material Requirement Elicitation is the process of identifying, discovering, extracting, clarifying, and understanding stakeholders' needs and expectations for a proposed software system — helping analysts understand business problems before proposing solutions. Requirements themselves don't solve problems, but they describe what the solution must do. They are first expressed in natural language, structured forms, sketches, and informal models before being refined into formal specifications.
Plain English Before you can build anything, you have to find out what people actually need — the way a tailor takes your measurements before cutting cloth, not after.

Two Pathways to Elicitation

  • Problem Analysis — identifying the problem, understanding its nature, and recognising constraints that may limit the solution.
  • Information Gathering (Fact-Finding) — the formal process of using research, interviews, questionnaires and other techniques to collect information about problems and requirements.

The Ishikawa (Fishbone) Diagram

Source Material A graphical tool to identify, explore and represent problems, their causes and effects. Also called the Cause-and-Effect Diagram, named after Kaoru Ishikawa (Kawasaki, Japan), a Total Quality Management pioneer.
  • Fish Head — name of the problem
  • Fish Bones — causes of the problem (usually 3–6)
  • Body — effects
The notebook adds: your diagram must use an even number of causes (4, 6, 8…), never odd.

Other modern elicitation techniques (slides): JAD (Joint Application Development) Sessions, Workshops, Brainstorming, Focus Groups, Prototyping, Storyboarding, User Stories, Scenarios.

The Fact-Finding / Elicitation Methods

Source Material — combining notebook + slides The five commonly used fact-finding techniques: sampling of existing documents, site visitation, observation, questionnaire, and interview.

1. Sampling of Existing Documents

Two ways: manual documents (organogram, medical files, OPD/IPD design) and computerised system documents (data dictionary, I/O interfaces, Data Flow Diagrams). Slides add key documents to review: organisational chart/mission statement/strategic plan, problem-area reports, policy/procedure/transaction manuals, interoffice memoranda and performance records, and — where a system exists — database samples, flowcharts, and design/program/operation documentation.

2. Site Visitation

Embraces experience from similar past problems, carried out three ways: Organisational visit (interact directly with the institution), Web visit (explore online resources of related organisations), Book visit / Literature Review (retrieve solutions from journals and reference books).

3. Observation ("Eye Witness Technique")

The analyst enters the working environment and watches staff perform duties to capture system flow. Steps: take permission from the organisation, observe diligently (not suspiciously), take note of observations.

Plain EnglishAdvantages: reliable data, relatively inexpensive, can correct descriptions from other techniques. Disadvantages: people may disguise their behaviour when watched, scheduling can be inconvenient, and it can interrupt work. Guideline: define the W5H (Why, Who, What, Where, When, How), get permission, inform those observed, don't disturb work, review notes with them afterward.

4. Questionnaire

Pre-prepared written questions administered to respondents.

TypeNatureExample
Open-ended (Free Format)Great latitude to respondent; responses non-uniform, poor for descriptive statistics"What is the cause of kidnapping in Nigeria?"
Close-ended (Fixed Format)Predefined responses to pick fromAgree / Disagree / Neutral

Unstructured (general goal, no specific questions) vs Structured (specific set of prepared questions) is another split noted on the slides. Advantages: convenient for large volumes of information, more reliable than observation, quick, easily tabulated. Disadvantages: inflexible, no chance to clarify incomplete answers, hard to design good standard questions.

5. Interview

Source Material An oral method of gathering data, involving pre-prepared questions for the respondent to respond to. Steps: book an appointment; prepare yourself psychologically (set alarm, plan questions); dress corporately; reintroduce yourself and your mission; explain your real mission; ask your questions; take permission for recording; observe body language; ask questions relating to their reaction; appreciate, exit, and replay the recording for further analysis.

Advantages: respondents answer freely, allows feedback, questions can be tailored. Disadvantages: time-consuming, location/distance challenges, success depends on the interviewer's interpersonal skill.

Deliverables & Challenges of Elicitation

Quick Revision Elicitation = discovering stakeholder needs via Problem Analysis (incl. Ishikawa, even number of bones) + Information Gathering (sampling docs, site visitation, observation, questionnaire, interview). Requirements don't solve problems — they describe what the solution must do.

Topic 3

Requirement Analysis

Definition

Source Material — combining notebook + slides Requirement analysis is the process of analysing, refining and restructuring raw requirements — thoroughly studying the application domain of the system to be developed, understanding the problem space, identifying stakeholder needs, and translating them into precise, actionable specifications developers can build against. It is the next major step after the feasibility study and elicitation.

The DIPM Process

Source Material
  • D — Detecting inconsistency in the raw requirement
  • I — Identify missing or ambiguous requirements
  • P — Prioritize requirements
  • M — Model the requirement (sketch/draw using draw.io, diagrams.net, app.diagram)

Types of Requirement Analysis

Functional Requirement, Non-functional Requirement, Domain Requirement.

Functional Requirements

Source Material Requirements that stipulate how a software should function — the expected operation of a software. The slides describe them as statements covering: Services Provided (core functions/operations offered), System Reactions (how the system responds to inputs/events), and Output Generation (results/reports/data produced).

Real-world example (AVERS System): users must specify their TYPE — Staff or Student — alongside username and password at login, a unique functional requirement enabling flexible filtering of access rights and data visibility per user category.

Functional requirements differ from general system requirements: general requirements are broad and apply to many systems, while functional requirements are specific and unique to the particular system's domain.

Non-Functional Requirements

Source Material Parameters that ensure the smooth operation of a software — called "constraints" because they indirectly but significantly influence implementation and design. Non-functional requirement types:
  • Product Requirement — standard operational requirement of the product: Performance (should beat optimal level), Security (software must be safe), Usability (must be usable), Reliability (fault tolerance expected).
  • Organization Requirement — Environmental (stakeholders dictate deployment environment), Development (stakeholders choose programming language), Operational (organisation can request partitioning of operation, e.g. user-level privilege).
  • External Requirement — Regulatory (policies from a higher controlling body), Legislative (constrains the software's jurisdiction), Ethical (rules governing group operation of the software).

Notebook distinction: Non-functional requirement relates to the system/software itself; Domain requirement talks about expertise and constraint from a specific field.

Domain Requirements

Source Material The constraint usually set by experts in a domain regarding the functionality of a software.
Quick Revision Requirement Analysis follows Elicitation and Feasibility Study, and runs on DIPM (Detect, Identify, Prioritize, Model). Functional = what the system does (services, reactions, output); Non-functional = how well it does it (Product/Organization/External); Domain = expert-set constraints from the field.

Answer: D — Detect inconsistency in the raw requirement; I — Identify missing or ambiguous requirements; P — Prioritize the requirements; M — Model the requirement by sketching/drawing it (e.g. with draw.io or diagrams.net).
Study Guide Reference: Topic 3 → The DIPM Process

Answer: Functional requirements define what the system should do — its services, reactions to input, and outputs (e.g. the AVERS login requiring a user TYPE field). Non-functional requirements define how well the system behaves — constraints such as performance, security, usability and reliability (e.g. a system must respond within 2 seconds).

Topic 4

Feasibility Study

Definition

Source Material A feasibility study is a systematic evaluation of a proposed software project to determine whether it is technically possible, economically worthwhile, operationally acceptable, legally compliant, and capable of being completed within the available time. It is one of the first activities in the Planning phase of the SDLC. Core question: "Should we build this system?" If the answer is No, the project should not proceed regardless of how attractive the idea seems.

Objectives of a Feasibility Study

  • Determine whether the project is worth pursuing before committing resources
  • Identify potential risks before development begins
  • Estimate project cost and expected benefits
  • Determine resource requirements (personnel, technology, infrastructure)
  • Assess organisational readiness to adopt/support the system
  • Support management decision-making with structured, evidence-based analysis

The TELOS Framework

Source Material The most widely accepted feasibility framework, with five core dimensions:
DimensionKey Question
TechnicalCan the system be built with available technology and expertise? Do we have qualified personnel?
EconomicIs the project financially worthwhile? (via Cost-Benefit Analysis)
LegalDoes the system comply with applicable laws and regulations?
OperationalWill users accept and use the system successfully?
ScheduleCan the project be delivered within the required timeline?

Many organisations also assess Organizational Feasibility (alignment with organisational goals/policy — e.g. University of Ibadan's e-Campus), Social Feasibility (impact on users/society — jobs, public acceptance) and Environmental Feasibility (energy consumption, e-waste, carbon footprint).

The notebook's version of this list (Technical, Economic, Operational, Scheduling, Legal) matches TELOS but in a different order — both name the same five core dimensions.

Feasibility Study Process & Report

Source Material Process: identify the business problem and proposed solution → collect relevant information → assess all five core dimensions (technical, economic, operational, legal, schedule) → prepare a feasibility report → present to management for a go/no-go decision.

Feasibility Report contents: Executive Summary, Background of the Project, Problem Statement, Proposed Solution, Technical/Economic/Operational/Legal/Schedule Feasibility, Risks, Recommendations, Conclusion.
AdvantagesLimitations
Supports informed decision-making; reduces project failure; identifies risks early; saves time and money; improves planning; helps secure management approval; ensures better resource allocationRequires time and cost to conduct; depends on the quality of available information; future conditions may change; incorrect assumptions may mislead conclusions

Topic 5

Software Development Process & Models (SDLC)

The Four Core Activities

Source Material Munassan et al. (2010): a software development process is an abstract description of a process defining how software is developed from a logical/strategic perspective. Activities: Software Specification → Software Development → Software Validation → Software Evolution. Pressman et al. (2010) frame this as a roadmap: Define → Build → Test → Deploy, carried out through Requirement, Development, Validation, and Operation & Maintenance respectively — involving Users & Developers, Developers, Developers, and Users & Developers again.

SDLC Stages

Planning → Requirement Analysis & Definition → Software System Definition → Implementation → Testing → Deployment → Maintenance.

Source Material SDLC is a representation of activities leading to the development of software. SDM (Software Development Model) refers to the acceptable methodology approach to developing software. (SDM ↔ SDLC)

Planning involves carrying out feasibility studies (see Topic 4).

Grouping the Models by Age

EraModels
Traditional (1970s–1990s)Waterfall, V-shape
Evolution (1990s–2000s)Evolutionary, Spiral
2001–2019Hybridisation of Agile & Waterfall
Modern (2020s–now)Agile-Scrum, DevOps

Waterfall Model

Source Material The oldest model, emphasising deep requirement definition and analysis before any development begins. Two schematic types:
  • Classical Waterfall: Requirement Definition & Specification → Software & System Design → Program Design → Implementation & Unit Testing → Integration & System Testing → Operation & Maintenance
  • Pure/Linear Waterfall: Software Requirement → System Requirement → Architectural Design → Detailed Design → Development & Unit Testing → Integration & System Testing → Deployment & Operation → Maintenance
AdvantagesDisadvantagesUsed in
Less error-prone; possibility of building robust softwareCostly; time-consuming; rigidFinancial, Military, Government apps

V-Shape Model

Source Material An extension of Waterfall that explicitly contains a "Planning" stage. The "V" stands for Verification and Validation — the model's other name. Left arm (Verification/Design): Planning → Requirement → Architectural Design → Detailed Design. Right arm (Validation/Testing): Unit Testing → Integration Testing → System Testing → Maintenance, meeting at Implementation at the base of the V.

Advantages: same as Waterfall. Disadvantage: more time-consuming due to the added planning stage.

Evolutionary Model ("Sharp-Sharp" Model)

Source Material Emphasises fast software development, laying little emphasis on requirement elicitation/analysis and jumping straight to specification and development. Three variants are drawn in the notebook:
  • Variant I — Requirement Specification ⇄ Demo Version ⇄ Development (relies heavily on domain requirement; also called the Incremental Model)
  • Variant II — Requirement Specification ⇄ Demo Version ⇄ Development, cycling toward a "Real Final" version (the Throwaway Prototype Model)
  • Variant III — Software Specification → Software Development → Software Validation → Deployment, producing a 1st Version, then Intermediate Versions, then a Final Version
Lecturer's note in the notebook: "If asked any evolutionary model, give me Variant III."

Spiral Model

Source Material The preferred model when security is the utmost priority; its major strength is risk analysis. Two variants drawn:
  • Variant I — four quadrants around a shrinking spiral: Planning, Risk Analysis, Development, Evaluation ("Next Phase?")
  • Variant II — the same four quadrants, but each ring is labelled with cycle stages: RA (Risk Analysis), PT (Prototype), D (Dev), T (Test), across repeating cycles (T1, T2, T3…)

Agile Model

Source Material Combines features of the Evolutionary and Spiral models; its agility makes it the most suitable model for hybridising with Waterfall. Components: Envision → Engage (Scrum/Sprint) → Release (Initial Version) → Review.

Lecturer's note: Differentiate Evolutionary from Agile, and justify which is best. Evolutionary: a single person can execute a project. Agile: it is about the team. Justification given: Agile is fast and depends on time.
Quick Revision Process: Specification → Development → Validation → Evolution. Roadmap: Define → Build → Test → Deploy. SDLC: Planning → Requirement Analysis → System Definition → Implementation → Testing → Deployment → Maintenance. Five models: Waterfall (rigid, sequential), V-shape (Waterfall + explicit planning + V&V), Evolutionary (fast, Variant III is the lecturer's preferred answer), Spiral (risk-driven, security-first), Agile (team-based, fast, hybridises with Waterfall).
